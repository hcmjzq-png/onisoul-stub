# 仓库整理与重构清单

审核基线为 2026-11-16 的 `205ac7a`（#77 合并后）。
这里的文件数、行数和 80/322 路由数均是该次基线；最新接线与口径核对见
[系统台账](project-status/README.md)和[本轮对齐记录](project-status/documentation-alignment.md)。
建议保留当前 Python 分层单体与 MySQL，先改善阅读入口、明确运行和候选代码边界，
再按职责拆分大文件。现有代码不足以说明需要更换语言、数据库或重建整个仓库。

## 为什么难读

基线受版本管理的文件共 678 个：`app` 61、`tests` 185、`docs` 340、`tools` 55、
`assets` 24，其余为配置、部署和根文件。这个数量不包含本地缓存、反编译产物和其他工作树。
主要复杂性来自三方面：

1. 历史研究量大，初期状态、后续修复和当前进度混在一起，阅读者很难知道哪份结论有效。
2. 业务目录同时放了已启用服务和研究候选；文件存在、测试通过都不能证明正式请求会执行它。
3. 少数文件承担了太多职责，且运行程序读取文档目录中的数据，使“清理文档”可能影响启动。

首页已经改成面向项目负责人的导航。详细进度只在 [系统台账](project-status/README.md) 维护；
旧研究保留证据，新的修正链接到最新结论。

## 哪些目录现在不能搬

六份 TSV 是当前源码直接读取的输入：

| 文件（均在 `docs/analysis/`） | 消费者 |
| --- | --- |
| `api_contract.tsv`、`behavior_contract.tsv`、`api_call_graph.tsv` | `app/business/contract.py` |

## 重构顺序

以下是后续任务，尚未执行。先保证模块职责清楚，再迁目录；每项独立 PR，保持可回退。

| 顺序 | 具体改动 | 为什么做 | 完成标准 |
| --- | --- | --- | --- |
| R1 登录、身份与数据库定义 | 从 577 行 `app/transport/login_page.py` 分离网页模板、账号校验和 SQL；把隐藏在页面中的 users 建表纳入明确的数据库管理流程 | 改页面不应牵连账号存储；目前 users 不在主 schema 中 | 原 Qt 保存/重开/清除、注册/登录/错误密码/会话回归；旧密码摘要与账号映射不变 |
| R2 玩法大文件 | 将 1353 行 `gameplay.py` 的账号/角色初始化、任务与奖励、建设职责逐步抽到对应服务，保留明确装配入口 | 一个文件横跨多个系统，容易多人冲突和误改其他功能 | 回包和存档前后等价，路由接入清单一致；每次只抽一项职责 |
| R3 运行清单与研究证据 | 将上述六份运行输入迁到独立契约/清单目录，统一路径访问 | 让 docs 真正只承担阅读与证据用途 | 六文件摘要保持，程序/测试/发布工具/文档引用全更新，干净检出能启动 |
| R4 正式服务与候选代码 | 建立统一接入清单；先标识，再将未挂载候选按系统分组 | `app/business` 有 42 个 Python 文件，存在不等于启用 | 不把候选自动开放；80 个专用/322 个其余入口保持相同，候选测试仍可单独运行 |
| R5 状态读写与重试边界 | 在现有存档/事务层统一业务保存入口；为新交易/步进设计可追踪的操作记录 | 当前多种写入方式需要明确同一次操作与重试的关系 | 并发、断线和提交结果未知时能回读确认；不能只拿请求参数哈希冒充操作身份 |
| R6 工具和研究测试 | 分类工具；将“验证旧补丁能套用”的历史测试与当前正式业务回归分层 | 大量脚本/历史检查增加理解和执行成本 | 常规回归不依赖应用历史补丁；研究复现仍有独立入口；保留实际行为覆盖 |

R1/R2 应和对应功能修复结合排期，避免长时间只搬代码却没有新的可用结果。
R3/R4 先保持行为不变；R5 的业务语义变化另做专项验收，不能藏进目录整理。
不同时拆微服务、替换数据库或给全部 JSON 存档设计新表，当前没有支持这种全面改造的证据。

## 以后保持清楚的规则

- 首页面向项目负责人，只保留常用阅读和启动入口；命令细节放开发/工具说明。
- 系统台账维护现状；研究报告保存某次证据，首页不再同时维护多套完成数。
- 新增候选必须说明未接入原因和接入条件；代码目录索引同步更新。
- 新工具说明读取什么、会写哪里、需要什么环境；测试数据库/账号操作不能标为只读。
- 每个 PR 标清代码、表、资源、本机工具分别是否需要发布；真机验收和 HTTP 验收分开。

本轮先完成阅读入口、索引、过时说明修正和两项小清理。服务端业务、数据库与资源目录的重构按上表后续落实。
